# ID Generation Design — Instagram-style, Database-Generated IDs
### GrowerCare · Design doc v0.2 · 2026-11-15
*Supersedes v0.1 (dedicated ID service). Decision 2026-11-15: **IDs are generated inside PostgreSQL**, following Instagram's sharded-ID design ([Sharding & IDs at Instagram](https://instagram-engineering.com/sharding-ids-at-instagram-1cf5a71e5a5c)). The application only routes by **country** (plus the grower, to pick the logical shard). It never builds IDs.*

---

## 1. Volume this must support (new estimate)

| Input | Value |
|---|---|

| Countries | 20 |
| Cases | 1 per user per day |

| Derived | Per country | Global |
|---|---|---|

| IDs incl. children (comments, activity, evidence ≈ 5×) | ~5K/s at peak | ~50K/s at peak |
| Hot cases (open + closed < 90 days) | ~1B+ | ~20B+ |

> ✅ **Confirmed 2026-11-15:** 1 case per user per day is the **worst case**. Comments from multiple actors come on top: 5–10 per case, which is 50–100M comments per country per day (see `05_CASE_COMMENTS_DESIGN.md`). This is far above the earlier "1,000 req/s total" target; §8 lists the knock-on changes.

At this size one database per country isn't enough, so **logical sharding is required**. That is exactly the problem Instagram's design solves.

---

## 2. The Instagram idea, applied

1. Each country's data is split into **64 logical shards**. Each shard is a Postgres **schema** (`in_s00 … in_s63`).
2. Logical shards are placed on a few **physical RDS clusters** (start with 4 clusters × 16 shards per country; scale by moving schemas, never by changing IDs).
3. A grower's data always lives in one shard: `shard = hash(grower_id) % 64`. A grower's cases, comments and activity are therefore single-shard queries.
4. **Each shard generates its own IDs with a PL/pgSQL function**, used as the column `DEFAULT`. No ID service, no coordination, no network hop.
5. **The ID encodes where the row lives** (country + shard). Any lookup by ID is routed directly, with no directory table.

```
App ──(country)──► country router ──► cluster map (country, shard) → RDS endpoint
         └──(grower_id)──► shard = hash(grower_id) % 64 ──► schema in_sNN
                                                         └─► INSERT … RETURNING case_id, case_no
                                                               (both generated by the DB)
```

## 3. Internal `case_id` (64-bit, generated in Postgres)

```
 0 | 41 bits: ms since 2026-01-01Z | 6 bits: country index | 6 bits: shard | 10 bits: sequence
   |   ~69 years (to ~2095)        |   64 countries        | 64 per country| 1,024 per ms per shard
```

| Field | Notes |
|---|---|
| Time (41) | `clock_timestamp()` of the DB server, custom epoch `1767225600000` (2026-01-01T00:00:00Z) |
| Country index (6) | From the country registry (e.g., IN = 46). Up to 64 countries. Region comes from the registry. |
| Shard (6) | Logical shard 0–63 within the country |
| Sequence (10) | `nextval(shard sequence) % 1024`, giving 1,024 IDs per ms per shard (≈ 1M/s per shard vs. a need of ~80/s) |

**Difference from Instagram:** Instagram used 13 shard bits with no country. We split those bits into **country (6) + shard (6)**, so the country (and therefore the region) can be read straight from the ID without a lookup.

```sql
-- Created per shard by a templated Flyway migration (placeholders: country_ix, shard_ix)
CREATE SEQUENCE in_s27.id_seq;

CREATE OR REPLACE FUNCTION in_s27.next_id() RETURNS bigint
LANGUAGE plpgsql AS $$
DECLARE
  our_epoch  CONSTANT bigint := 1767225600000;  -- 2026-01-01T00:00:00Z
  country_ix CONSTANT int    := 46;             -- IN
  shard_ix   CONSTANT int    := 27;
  now_ms     bigint;
  seq        bigint;
BEGIN
  seq    := nextval('in_s27.id_seq') % 1024;
  now_ms := floor(extract(epoch FROM clock_timestamp()) * 1000);
  RETURN ((now_ms - our_epoch) << 22)
       | (country_ix << 16)
       | (shard_ix   << 10)
       | seq;
END $$;
```
The same `next_id()` serves cases, comments, evidence and activity in that shard. All of them are globally unique because country + shard are in the bits.

**Decoding (app/support tool, no DB call):**
`ms = (id >> 22) + epoch` · `country = (id >> 16) & 63` · `shard = (id >> 10) & 63` · `seq = id & 1023`

## 4. Public `case_no` (15 digits, generated in Postgres)

12 digits can no longer hold the volume: 10M cases per country per day needs a 7–8-digit daily counter. The public number grows to **15 digits** and also carries the shard, so a phone/IVR lookup is routed directly too.

```
  7 1   0 3 1 8   2 7   4 8 2 1 3 9   6
  └CC┘  └DDDD─┘   └HH┘  └─SSSSSS──┘   └K
  CC     country slot (10–98; region implied by range, 00–09 reserved, 99 sandbox)
  DDDD   day number since 2026-01-01 in the country's reference timezone
  HH     logical shard 00–63
  SSSSSS per-shard counter (mod 1,000,000) → 1M per shard per day = 64M per country per day
  K      Damm check digit
```
Example **`71-0318-27-482139-6`**: India, 2026-11-15, shard 27, counter 482139, check digit 6 (valid).

```sql
CREATE SEQUENCE in_s27.case_no_seq;

CREATE OR REPLACE FUNCTION in_s27.next_case_no() RETURNS char(15)
LANGUAGE plpgsql AS $$
DECLARE
  cc     CONSTANT text := '71';
  shard  CONSTANT text := '27';
  tz     CONSTANT text := 'Asia/Kolkata';
  day_no int    := (clock_timestamp() AT TIME ZONE tz)::date - DATE '2026-01-01';
  seq    bigint := nextval('in_s27.case_no_seq') % 1000000;
  body   text   := cc || lpad(day_no::text, 4, '0') || shard || lpad(seq::text, 6, '0');
BEGIN
  RETURN body || public.damm_check_digit(body);   -- shared IMMUTABLE function
END $$;
```
- The counter **never resets**; it wraps every 1M values. A (day, shard) can only collide if one shard issues > 1M cases in one day. The average is ~156K per shard per day (10M / 64), so there's ~6× headroom. A `UNIQUE` constraint is the final guard, and an alert fires at 60%.
- No daily reset means no hot "counter row" and no locking. It's just a sequence.

### The table
```sql
CREATE TABLE in_s27.cases (
  case_id    bigint   PRIMARY KEY DEFAULT in_s27.next_id(),
  case_no    char(15) NOT NULL UNIQUE DEFAULT in_s27.next_case_no()
             CHECK (case_no ~ '^[1-9][0-9]{14}$'),
  country    char(2)  NOT NULL CHECK (country = 'IN'),
  grower_id  bigint   NOT NULL,
  case_type  text     NOT NULL,
  status     text     NOT NULL,
  -- …
  created_at timestamptz NOT NULL DEFAULT now(),
  version    int      NOT NULL DEFAULT 0
);

-- Application:
INSERT INTO in_s27.cases (country, grower_id, case_type, status, …)
VALUES ('IN', :grower, :type, 'SUBMITTED', …)
RETURNING case_id, case_no;
```

## 5. What the application does (and doesn't do)

| Application does | Application does **not** |
|---|---|
| Picks the cluster from **country** (and data residency) | Generate or format IDs |
| Picks the schema from `hash(grower_id) % 64` | Call any ID service |
| Reads `case_id`/`case_no` from `RETURNING` | Keep counters |
| Decodes IDs to route reads: `/cases/{case_id}` → country + shard bits; `case_no` → CC + HH digits | Need a directory table to find a case |
| Serializes IDs as **strings** in JSON (JS can't hold 64-bit integers exactly) | |

**Shard map** (config, versioned): `(country, shard) → cluster endpoint`. Moving a shard to a new cluster (logical replication of one schema, then cutover) changes only this map. IDs never change.

## 6. Weak points of DB-generated IDs, and mitigations

| Risk | Why | Mitigation |
|---|---|---|
| **DB clock jumps back** (NTP step, failover to a standby with clock skew) | Time comes from the DB server | RDS keeps hosts NTP-synced. Alarm on clock-skew metrics. Duplicates also need the same `seq % 1024` in the same ms on the same shard, which is very unlikely. `PRIMARY KEY`/`UNIQUE` reject them and the app retries the insert once. |
| **Sequence after failover** | — | Postgres sequences only move **forward** after crash/failover (values are WAL-logged ahead), so they never repeat. |
| **> 1,024 IDs/ms in one shard** | Wraps within the ms | Need is ~80/s per shard; bulk backfills use a separate sequence range or throttling |
| **ID only known after insert** (v0.1 had pre-insert IDs) | DB assigns on `INSERT` | Photo uploads use a client UUIDv7 staging key, then link to `case_id` after insert. Or create the case in `DRAFT` first, then upload. |
| **Offline / WhatsApp intake** | No DB reachable | Device keeps a draft with a UUIDv7 idempotency key; `case_no` is assigned when the sync insert happens and is sent back to the grower |
| **1,280 schemas to migrate** (20 countries × 64) | Every migration runs per shard | Flyway with placeholders, run by a migration orchestrator per cluster. Expand → migrate → contract only. CI checks that all shards share one schema version. |
| **Country index exhausted** (64) | 6 bits | Enough for 20 countries + 3× growth. Beyond that, v2 layout (reserved leading `0` in `case_no`, new epoch bit split). |
| **Business volume leakage** (counter differences within a day) | Sequential counters | "Track my case" requires `case_no` + OTP. Optional P2: keyed permutation of `SSSSSS` inside `next_case_no()` (pgcrypto HMAC-Feistel, key in a restricted table). |

## 7. How this fits the data platform (doc 03)

- **Debezium:** one connector per **physical cluster**, capturing `in_s*.cases` etc. The `ByLogicalTableRouter` transformation merges all shard schemas into one topic per table (`cdc.in.cases`). Because IDs are globally unique, the merged key is safe. Kafka key = `case_id`.
- **Snowflake:** a single `CURATED.CASES` table per regional account, with no ID clashes across shards or countries; clustered by `(country, created_day)`.
- **Archive stubs:** `archived_record_index` lives in the same shard as the case; lookups by `case_no` route by CC + HH as for hot data.
- **Purge:** runs per shard, so archive work is naturally parallel.

## 8. Knock-on changes if the volume is confirmed
| Area | Earlier assumption | Now |
|---|---|---|
| Peak load (NFR) | 1,000 req/s total | ~20K writes/s + reads (likely 100K+ req/s) globally |
| RDS per country | 1 Multi-AZ instance | 4 → 16 clusters per country (64 logical shards) |
| CDC volume | ~1K events/s per cell | ~25–50K events/s per large country at peak; MSK sized per country |
| Snowflake | ~1–2 TB/year per cell | Hundreds of TB/year; cost model and clustering become a first-class design topic |
| Hot storage | Hundreds of GB | ~5–10 TB per country, spread across shards |

## 9. Requirements (replace ID-1 … ID-12 from v0.1)
| ID | Requirement | Pri |
|---|---|---|
| ID-1 | `case_id` is a 64-bit ID generated by a per-shard PostgreSQL function: 41-bit ms time, 6-bit country, 6-bit shard, 10-bit sequence | M |
| ID-2 | `case_no` is a 15-digit number generated by a per-shard PostgreSQL function: CC + DDDD + HH + SSSSSS + Damm digit | M |
| ID-3 | Applications never generate IDs. They route by country (cluster) and `hash(grower_id) % 64` (schema) and read IDs from `RETURNING` | M |
| ID-4 | Any read by `case_id` or `case_no` is routed by decoding the ID; no directory lookup | M |
| ID-5 | Country registry holds country index (6-bit), public CC slot, region, reference timezone; never reused | M |
| ID-6 | Shard map `(country, shard) → cluster` is versioned config; moving shards never changes IDs | M |
| ID-7 | `PRIMARY KEY`/`UNIQUE` constraints on both IDs; a uniqueness violation triggers one retry + sev-2 alert | M |
| ID-8 | IDs serialized as strings in JSON; `case_no` stored as `CHAR(15)` | M |
| ID-9 | Check digit validated in UI, API and IVR before lookup | M |
| ID-10 | Capacity alerts: per-shard daily `case_no` usage at 60%, per-shard IDs/ms headroom | M |
| ID-11 | Offline/WhatsApp drafts use UUIDv7 idempotency keys; `case_no` assigned on sync | P2 |
| ID-12 | Optional keyed permutation of the `case_no` counter to hide volumes | P2 |
